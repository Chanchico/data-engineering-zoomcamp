# ex-001 — Why chunks, why explicit types? — My answers and review

📄 [Exercise statement](../../exos/module-01/ex-001-ingestion-concepts.md)

## 1. `DtypeWarning` on column 6

**My answer**

This is because column 6 has multiple data types across the whole file, but not in the first hundred rows. It can be a problem because databases have strict rules about data types, and the ingestion will fail with an error.

**Correction : partiel**

- Bonne idée : le type n'est pas homogène sur tout le fichier.
- Il manque le mécanisme. Pandas lit le fichier par blocs internes et devine le type de chaque bloc séparément. Sur 100 lignes il ne voit qu'un seul bloc, donc aucun conflit. Sur le fichier complet, certains blocs donnent des `str` (`Y`/`N`) et d'autres des `NaN`, ce qui donne une colonne `object` au type mixte.
- Pour la base, le risque est un schéma deviné à partir d'un échantillon. Une valeur d'un autre type, vue plus tard, peut faire échouer l'insertion, et le schéma peut changer selon le fichier lu.

## 2. Benefit of `chunksize=100000`

**My answer**

The benefit of `chunksize` is that it does the ingestion progressively, which allows the database engine not to be overused and avoids a possible overload error on the database server. It is also better because, if an error occurs in a chunk, we can target that error.

**Correction : partiel**

- Bonne idée générale, mais l'exercice demandait deux problèmes concrets de l'approche en un seul `to_sql`, et tu n'en nommes pas vraiment.
- Le problème principal est la RAM du client : un DataFrame d'une année entière peut ne pas tenir en mémoire. Ce n'est pas la base qui est surchargée.
- Avec un seul `to_sql`, tout est en une seule transaction : une erreur au milieu annule tout, et tu n'as aucun suivi de progression.
- Ton argument « on cible l'erreur dans un chunk » est valable.

## 3. `head(n=0).to_sql(..., if_exists="replace")`

**My answer**

Dans cette partie du code, on crée et on ajoute le premier chunk dans la table. Dans le cas où la table existe, on l'écrase, d'où le `replace`. Si on laisse `replace`, nous supprimons les données déjà chargées.

**Correction : erreur de compréhension**

- `head(n=0)` n'insère **aucune ligne**. Ça crée seulement la table vide, avec les colonnes et les types du DataFrame. Tu écris que ça « ajoute le premier chunk », ce qui est faux.
- La raison de ce choix, que tu ne donnes pas : après ça, la boucle peut faire `append` pour tous les chunks, y compris le premier, sans cas particulier.
- Ta réponse sur `replace` dans la boucle est juste : chaque chunk supprimerait la table et il ne resterait que le dernier, soit environ 69 765 lignes (1 369 765 − 13 × 100 000) au lieu de 1,37 million.

## 4. Extra column added by `to_sql`

**My answer**

The added column is named `index`. It seems to be a counter that is incremented each time the database writes a new row.

```text
               ^
Time: 0.016s
root@localhost:ny_taxi> SELECT COUNT(*) FROM yellow_taxi_data
+---------+
| count   |
|---------|
| 1369765 |
+---------+
SELECT 1
Time: 0.478s
root@localhost:ny_taxi>
```

**Correction : bon nom, mauvaise origine**

- La colonne `index` est correcte.
- Ce n'est pas un compteur de la base. C'est l'index du DataFrame pandas, écrit en colonne parce que `index=True` par défaut dans `to_sql`. Il ne vient ni de Postgres ni d'une insertion.
- La solution est `index=False`.
- La sortie collée ici est un `COUNT(*)`, qui n'a rien à voir avec la question. Le critère d'acceptation demandait de confirmer avec `\d yellow_taxi_data` dans pgcli : colle cette sortie ici.

## 5. Running the ingestion twice

**My answer**

Yes, the behavior is idempotent because the script reproduces the same result each time:

```text
               ^
Time: 0.016s
root@localhost:ny_taxi> SELECT COUNT(*) FROM yellow_taxi_data
+---------+
| count   |
|---------|
| 1369765 |
+---------+
SELECT 1
Time: 0.478s
root@localhost:ny_taxi>
```

**Correction : bonne conclusion, justification faible**

- Oui, c'est idempotent, et 1 369 765 est bien le total de janvier 2021.
- Ta raison, « le script reproduit le même résultat », est circulaire. La vraie raison : la cellule recrée la table avec `if_exists="replace"` au départ, ce qui supprime les anciennes données. Si tu ne relançais que la boucle `append`, tu aurais environ 2,74 millions de lignes.
- L'exercice demandait d'écrire le compte attendu **avant** de lancer. Je ne vois pas de prédiction, seulement le résultat.
- Nuance : l'idempotence vient ici de « tout supprimer puis tout recharger ». Pendant le chargement, la table est vide ou partielle, et ce n'est pas atomique.
